# 01 - Architecture and Terminology

_Reflects local branch `fix/code-node-development-best-practices` = upstream v1.15.0 + Code Node commit `030e9c6`. See `00-Overview.md` for source state._

---

## The major components, in one glance

- **Engine** - the npm package `@cognigy/plugin-engine` (bins `cognigy-mcp`, `cognigy-setup`). A stdio MCP server, one process per client session, exposing 17 tools over the Cognigy REST API. Lives in `src/`.
- **Plugin wrapper** - the `plugin/` directory: four parallel manifest trees plus 15 skills and 2 subagents. Same version number as the engine, enforced by scripts. Contains no executable code.
- **Tool layer** - `src/tools/definitions.ts` (what the model sees), `src/schemas/tools.ts` (Zod validation), `src/tools/handlers.ts` (6,600 lines; one `handleXxx` per tool behind a `switch` in `handleToolCall`), plus extracted pure-logic modules (`nodeRegistry`, `codeNodeValidation`, `toolParameters`, `packageManagement`, `snapshotManagement`, `voiceChecklist`, `webchatSettings`, `filters`).
- **API client** - `src/api/client.ts`: axios, `X-API-Key` auth, 30 s timeout, 3 retries on 429/5xx/network errors, optional `X-Ask-AI-Context` audit header. No pagination helper; handlers page ad hoc.
- **Always-on instructions** - `src/instructions.ts`, 43 lines injected as the MCP server `instructions` field on every session. The baseline for clients that do not load skills (Codex).
- **Skills** - `plugin/skills/<id>/SKILL.md`, intent-triggered guidance. This is where most Cognigy platform "gotchas" and best practices live today, as prose the model reads, not as code the server enforces.
- **Subagents** - `plugin/agents/*.md`: `cognigy-agent-builder` and `cognigy-voice-go-live`, isolated-context workers for Claude Code (and Cursor). Not available on Codex.
- **Backup gate** - in-memory, per-process hold in `handleToolCall` that refuses the first mutating call against an existing resource per project until the model has offered a Cognigy Snapshot and the user has accepted or declined.
- **Installer and client platforms** - `src/setup.ts` wizard plus one module per client in `src/install/` (Claude Code, Claude Desktop, Codex, Gemini CLI, Antigravity, "other hosts"). Cursor needs no installer.
- **Release and CI plumbing** - `scripts/*.mjs` (version sync, manifest check, asset copy, Gemini extension build, local dev marketplace), semantic-release on `main`, husky + commitlint, two GitHub workflows. **`scripts/` is release automation, not tests.** Tests are `src/__tests__/*.test.ts` (24 files, Jest).
- **Configuration** - one base URL and one API key per process, from env vars or `~/.cognigy-plugin/config.json`. No profile or multi-tenant concept.

## The constraint that shapes everything else

The upstream maintainer distributes this as **one universal codebase** across seven client platforms (Claude Code, Claude Desktop, ChatGPT + Codex, Gemini CLI, Antigravity, Cursor, Agent-Plugins-spec hosts such as Kiro and VS Code + Copilot). The repo's own rules encode this: every manifest pins the same version (`scripts/sync-plugin-version.mjs`), `check-plugin-manifest.mjs` fails CI if any of six manifests drift, and the contributor skill `add-client-platform` states the "one-version rule" and forbids client-specific forks of the engine. The Phase 0 case study (the Code Node PR) exists partly to learn how the maintainer reviews contributions and what he will absorb upstream versus what stays fork-only.

Two planning consequences follow. First, anything the fork adds to `src/` lands in every platform at once; there is no "NA PS build" switch in the codebase today. Second, every client platform the fork keeps supporting is a tax paid on every release (the roadmap's open decision on which platforms the team actually needs). The maintainer-side expectation of a single codebase is reported from the team's planning discussions and the repo's contributor rules; it was not independently confirmed with him in this pass.

Upstream also moves, and the cadence is bursty rather than periodic: v1.16.0, v1.17.0 and v1.18.0 all shipped on 2026-09-15 within two hours (12:49, 13:45, 14:46 UTC), while v1.8.1 to v1.8.2 took nearly 17 days. As of this update, upstream is at v1.18.0; the fork is four releases behind. Any fork strategy has to budget for event-driven, not calendar-driven, rebasing - see the cadence section of `ai-coe-plugin-workspace/strategy/Maintenance-Strategy.md`.

## How a tool call actually flows

A client sends `CallTool` over stdio. `src/index.ts` rate-limits by API-key prefix (100 calls per 60 s, fixed window, applies to MCP calls not to outbound HTTP), opens an `AsyncLocalStorage` task id for audit attribution, and calls `ToolHandlers.handleToolCall(name, args)` (`handlers.ts:6517-6604`). Before dispatch, the **backup gate** decides whether to hold the call (`:6526-6535`). Then a `switch (toolName)` routes to `handleXxx`, each of which begins with `schemas.xxxSchema.parse(args)`. Results are `JSON.stringify`'d into one text block; errors come back as `{error, status, code, traceId}` with `isError: true`. After dispatch, `learnProjectIds(result)` records which project a returned resource belongs to, which is how the gate scopes itself per project without an extra API call.

What this means for planning: adding a tool is mechanical (definition + schema + handler case + skill + tests, see 03), but adding an **enforced rule** that must run for many tools has no home. There is no general "validate this node's content" dispatch; `codeNodeValidation.ts` is wired at four specific call sites (three Zod `superRefine`s in `schemas/tools.ts:311-395` plus one pre-PATCH check in `handlers.ts:4291-4303`). That is why the Code Node PR touched 9 files, and why the roadmap's Phase 2 "validation registry" is an architecture proposal rather than a nice-to-have.

## Two ID systems

Cognigy exposes two identifiers per resource and the plugin uses both. `_id` is a 24-hex Mongo id and is what most operations take (Zod `idSchema`). `referenceId` is a UUID and is what cross-resource pointers use: `flowId` inside an endpoint, `llmProviderReferenceId` in the Job node, `knowledgeStoreReferenceId` on the agent, `knowledgeStoreId` inside a knowledge tool node, connection ids, and `localeId` on endpoints (the 1.13.0 fix stored the wrong one). Skills consistently say "`<flow referenceId>`" when they mean the UUID. Roadmap items that hand ids between tools (the proposed `create_flow` returning `flowId`/`referenceId`) need to return both.

## Where guidance lives versus where enforcement lives

This distinction matters more than any other for the "Embedded Best Practices" phase, so it is worth stating plainly.

| Layer                                  | Runs when                                                                                                                                     | Can block a bad write?                | Examples today                                                                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `src/instructions.ts`                  | Every session, every client                                                                                                                   | No (prose)                            | "Never add nodes before the AI Agent Job node"; default `toolType` is `tool`                      |
| `plugin/skills/*/SKILL.md`             | When the client's skill loader matches intent (Claude Code, Cursor, Codex, Antigravity, Gemini; **not** Claude Desktop without in-app plugin) | No (prose)                            | Code Node standardized catch block, `api.*` allowlist, param-schema rules, voice defaults         |
| Tool `description` in `definitions.ts` | Every session (part of the tool list)                                                                                                         | No                                    | `setup_llm` "PRECONDITION... STOP"                                                                |
| Zod schemas in `schemas/tools.ts`      | Every call, before the handler                                                                                                                | **Yes**                               | Code Node try/catch, `toolParameters` normalization, provider enums                               |
| Handler logic in `handlers.ts`         | Every call                                                                                                                                    | **Yes**                               | `requiredConfigKeys` check for node create, backup gate, branch `appendChild` to `append` rewrite |
| `nodeRegistry.ts`                      | On `manage_flow_nodes create`                                                                                                                 | **Yes** (unknown `nodeType` rejected) | 15 node types                                                                                     |

`src/policy/` is the designated home for enforced rules once it exists, sitting alongside the Zod/handler/registry rows above.

Only the bottom three rows are enforcement. Everything the NA PS standards say about Task nodes, Overwrite Analytics, initiation flows, and naming currently has nowhere to go but the top three rows, unless new code is added.

## Terms from NA PS standards that have no plugin counterpart yet

Listed here so a planning conversation does not go looking for them in the code: T-shaped agent pattern, initiation flow / session setup flow, `Topic - Category - Outcome` task naming, `Attempted` / `Successful` / `Unsuccessful` goal states, `customN` analytics fields, `handoverEscalations`, Once node, `API - <Topic>` flow naming, reference corpus, Pass-grade build. All of these are vocabulary from the team's standards (`na-professionalservices`, `cognigy-build-qa-auditor`) and the SME architecture recommendation, and they appear in the codebase only as a citation in the header comment of `codeNodeValidation.ts:2-8`.
